# License policy

BadgeDay is closed-source commercial software. A dependency may ship only when
its license is permissive, or when `license-exceptions.toml` records a review
of a specific non-permissive license.

## What may ship

The allowed SPDX identifiers are `.github/license-allowlist.txt`. That list is
MIT, MIT-0, Apache-2.0, BSD-2-Clause, BSD-3-Clause, ISC, 0BSD, Unlicense,
Python-2.0, PSF-2.0, BlueOak-1.0.0, the Boost and zlib licenses, CC0-1.0,
CC-BY-3.0 and CC-BY-4.0 (attribution only), and the other permissive
identifiers written there. CC-BY-SA is not on the list.

A dual-licensed package passes when one complete alternative is made only of
identifiers on that list. The other alternative is still reported. `MIT OR
GPL-2.0-only` passes on MIT. `GPL-2.0-only OR Ruby` does not: the Ruby
license's modification terms are not permissive, and it is not on the allow
list. `MIT AND GPL-2.0-only` does not pass.

GPL, AGPL, LGPL, SSPL, MPL, EPL, and any license the check cannot identify
fail the build.

## Exceptions

`license-exceptions.toml` is the only place a non-permissive package is
allowed. Each row names the ecosystem (`pypi`, `npm`, or `gem`), the package,
the canonical license expression CI prints, why it may ship, `approved_by`,
and the date. `version` pins that review to one release. A newer release is
not covered until the row is updated. An empty field does not approve
anything. The Ruby license stays off the allow list; a gem that needs it is
an exception row, not an allow-list change.

Add a row only after a person has accepted the obligation. Do not add one
merely to turn CI green.

## Where CI looks

`.github/workflows/licenses.yml` runs on pull requests and on pushes to `main`.

Dev dependencies are in scope, not only packages that ship in the runtime
image. That includes the Python `dev` extra, npm `devDependencies` (direct and
transitive), and the Fastlane gem set.

The repo's own packages are not dependencies. `badgeday` (the Python project)
and the private npm roots (`web`, `badgeday-ios`, `private: true`, no SPDX
license) are excluded. A third-party package marked `UNLICENSED` still fails.

Install scripts are not run while the tree is installed for this check:
`npm ci --ignore-scripts`, and `pip install --only-binary=:all:` so a
dependency cannot execute `setup.py`. An unreadable directory in those
installed trees fails the job; it is not skipped.

- Python: `pip install --only-binary=:all: -c .github/license-constraints.txt -e ".[dev]"`
  plus `deploy/play-verify/requirements.txt`, including transitive packages.
  `pip-licenses` is installed with the same constraint and cross-checks that
  inventory. There is no Python lockfile. The constraint file is used only by
  this job and pins certifi to the release in `license-exceptions.toml`, so a
  newer certifi on PyPI does not enter the scan. The `ops` extra is not
  installed. It is migration tooling (`scripts/apply_migrations.py`), not
  part of the app image and not part of this scan. Packages in the `ops`
  extra are excluded from the scan and need a manual license review when added.
- npm: `web/package-lock.json` and `mobile/ios/package-lock.json`, including
  dev, transitive, and optional platform packages. Installed trees are
  cross-checked with `license-checker-rseidelsohn` (pinned to 4.4.2, the
  current release that still runs on Node 20).
- Ruby: `mobile/ios/Gemfile.lock`, from the RubyGems license metadata and the
  license files inside the published gem when that metadata is missing or not
  permissive.

`actions/dependency-review-action` applies the same allow list to dependency
changes in a pull request. It does not see packages already on `main`, and it
does not fail when GitHub cannot name a license. The full-tree job does both.

Android Gradle dependencies are generated by bubblewrap when the Trusted Web
Activity is built. They are not locked in this repo, so this check does not
see them. CocoaPods are generated from the Capacitor plugins during the iOS
build; those plugins are scanned as npm packages.
