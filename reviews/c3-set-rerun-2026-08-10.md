## Two answers produced no critique, and neither is a rubric finding

The report printed both under *"these are the clauses to rewrite"*, which is wrong and is the
first thing fixed below. Two distinct infrastructure defects:

### H — an empty field, rejected by our own validator against a rule the model never saw

```
points.1.source_id    String should have at least 1 character
points.1.observation  String should have at least 1 character
```

Complete, correctly-shaped JSON with two empty fields. It was filed as a schema violation and
**not retried**, per the reasoning in `app/llm_output.py` that a wrong-shaped response will come
back wrong again.

**That reasoning does not hold here.** `messages.parse` strips `min_length` and the other
constraints structured outputs does not accept from the schema it sends, then re-validates them
client-side. So the API enforced a schema in which `""` is legal, the model returned something
legal under it, and the rejection happened on our side against a rule it was never given. Not
truncation, and not the model returning the wrong shape — **a third category the module did not
have**, and asking again does help, because there was no rule being broken to break twice.

### I — truncation on both attempts, at a budget we set

`max_tokens` was 16,000 and caps thinking *plus* the JSON body. At effort `high` with adaptive
thinking the reasoning is the larger half, and the critique body is far bigger than the scorer
prompt the 16k figure was chosen against. Two of eleven answers stopped mid-JSON; one recovered
on its retry, and I did not.

## Fixes

**1. A third failure category, retryable.** `is_unenforced_constraint` in `app/llm_output.py`
returns true when **every** error is a constraint the API was never asked to enforce. `all`
rather than `any` is the whole care in it: an empty string *alongside* a missing field is a real
schema defect that happens to contain an empty string, and retrying it would spend a call to
hide a bug. `UnenforcedConstraint` is its own exception rather than reusing `TruncatedOutput`
because the follow-up differs — a truncation wants more room, this wants the prompt to state a
rule the schema cannot carry across the wire.

**2. The prompt now states that rule**, so the retry is the fallback rather than the mechanism:
*a point you cannot describe is a point you must not emit.*

**3. `MAX_TOKENS` 16,000 → 32,000**, with an explicit per-request timeout, because the raised
ceiling is near where the SDK starts refusing non-streaming calls on its own timeout estimate.
If truncation recurs at this budget the answer is to stream the call rather than keep raising
the number — but streaming loses `parsed_output`, so that is a real change and not worth making
before it is needed.

**4. A failed answer is no longer reported as a divergence.** It is counted separately, marked
`!!` rather than `<>`, prints *"no critique produced"* instead of a clause it never named, and
the exit code is non-zero so a set re-run with holes cannot go green. The header now says
plainly that the anchors were never asked.

This is the same false-divergence failure `app/llm_output.py` was written to prevent, one layer
up: a calibration report is worth having only if its divergences can be trusted, and it had two
that were not divergences.

## Observed, not fixed

**F is a 4 wearing the wrong route tag.** It came back **4b** — *"handles people; appetite
unproven… the relationships in his stories are transactional, and nobody in them appears to
matter to him beyond the task."* That is not F. Asking after a colleague's mother and declining
to escalate over his head is neither transactional nor indifferent. The pipeline had to pick a
route and picked the one that fits least badly.

B and K also came back 4b, and D came back an unrouted 4. **Three of four level-4 answers landed
on the same tag**, which is what a split does when it has nowhere to put a case. This was flagged
as a prediction when the third route went into anchor 4 without a tag; it is now an observation,
and it is fresh evidence for the standing question in §10 about whether the 4A/4B split should
survive at all. The split is drawn on wanting-versus-able, and this class of answer is neither.

## Disposition

**The breadth clause is confirmed on the evidence available**: it moved the answer it was aimed
at, left the answer it was not aimed at alone, and disturbed none of the other seven. The claim
is one run of one call per answer — enough to see a band change, not enough to speak to
stability at any boundary.

**Re-run needed for I**, and worth re-running the whole set at the same time now that the two
failure paths are fixed. `scripts/recruit_noise_floor.py c3` is also still stale, from two rounds
of anchor edits.
